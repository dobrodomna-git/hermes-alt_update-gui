# Задача: `hermes_update_gui.py` — графическая обёртка обновления Hermes

## Контекст (факты, проверенные на живой машине)

- Windows 11. Hermes стоит в `C:\Users\domna\AppData\Local\hermes\hermes-agent` (git-чекаут).
- Апдейтер: `venv\Scripts\hermes.exe update --branch main --yes --keep-stash`.
- Python с Tkinter: `venv\Scripts\pythonw.exe` (Python 3.11, tkinter 8.6) — GUI-скрипт должен
  запускаться ИМЕННО им (без консоли). Сам скрипт: `hermes_update_gui.py`, один файл, stdlib-only
  (tkinter, subprocess, threading, queue, time, os, sys, re). Никаких pip-зависимостей.
- Кодировка файла UTF-8, первая строка `#!/usr/bin/env python3`, вторая `# -*- coding: utf-8 -*-`.
  Весь интерфейс на русском. В .py можно кириллицу.
- Реальный апдейтер пишет в stdout/stderr строки с маркерами этапов (ниже — точные образцы из
  живого лога). Он НЕ даёт процентов — проценты выводит только по этапам (см. «Прогресс»).
- Долгий этап «Building desktop packaged app» может молчать >10 минут. Поэтому апдейтер запускается
  с переменной окружения `HERMES_UPDATE_STEP_IDLE_SECONDS=1800`.
- Во время этапа пересборки десктопа само приложение Hermes закрывается апдейтером — это нормально,
  GUI-окно обёртки должно продолжать жить (оно отдельный процесс).

## Что должно получиться

Одно окно Tkinter (~880x620, тёмная тема), которое:

1. Запускает апдейтер как дочерний процесс и читает его stdout+stderr построчно (отдельный поток,
   строки через queue.Queue в UI-поток; UI обновляется только через `after()` — из потока напрямую
   tkinter не трогать).
2. Классифицирует каждую строку по этапам (список ниже), обновляет:
   - чек-лист этапов (галочка ✓ / спиннер / ✗ / серый «ожидается»),
   - полосу общего прогресса (по весам этапов),
   - лог-панель (авто-скролл, моноширинный, максимум 2000 строк в виджете, лишние отбрасывать),
   - счётчики: «соединений», «загрузок», «ошибок» (см. паттерны).
3. Пишет ВСЁ (и строки апдейтера, и свои события обёртки с префиксом `[gui]`) в лог-файл
   `%LOCALAPPDATA%\hermes\logs\update-gui-<ГГГГ-ММ-ДД-ЧЧММСС>.log` (UTF-8, flush построчно).
4. По завершении процесса:
   - exit code 0 И в вылове была строка `Update complete` → зелёный баннер
     «ОБНОВЛЕНИЕ ЗАВЕРШЕНО» + строка версии из лога (вид: `v0.21.5+3722... → v0.21.5+5842... [main @ a28aaa1edfe]`)
     + текст «Закройте это окно и запустите Hermes заново (ярлык на рабочем столе).»
   - иначе → красный баннер «ОБНОВЛЕНИЕ ПРЕРВАНО / ОШИБКА» + exit code + последние 5 строк,
     начинающихся с `✗` или `[ERROR]` или содержащих `failed`, + путь к лог-файлу
     + текст «Закройте установщик; подробности в логе (кнопка «Открыть лог»).»
   - кнопки в финальном состоянии: «Открыть лог» (os.startfile лог-файла), «Открыть папку Hermes»
     (os.startfile `%LOCALAPPDATA%\hermes`), «Свернуть лог» не нужна.
5. Кнопка «Отменить» (активна до финала): убивает дочерний процесс (subprocess.Popen.terminate,
   через 3 с kill), ставит статус «отменено пользователем», финальный баннер жёлтый
   «ОБНОВЛЕНИЕ ОТМЕНЕНО». Крестик окна = то же самое (WM_DELETE_WINDOW → отмена + destroy).
6. Таймер раз в 1 с: «время: мм:сс», и если >120 с без новых строк апдейтера — жёлтая строка
   «этап идёт N мин без вывода — это нормально для сборки десктопа» (не ошибка).

## Этапы (канон; порядок фиксирован)

Каждая строка апдейтера матчится по подстроке (регистронезависимо) и относится к этапу;
переход на новый этап = предыдущий завершён ✓. Этапы и веса прогресса:

| # | id | Название в UI | Маркер(ы) старта (подстрока в строке лога) | вес |
|---|----|---------------|--------------------------------------------|-----|
| 1 | prep | Подготовка и остановка Hermes | `Stopping Windows gateway`, `stopping`, `preparing update` | 5 |
| 2 | fetch | Соединение с репозиторием | `Fetching updates` | 10 |
| 3 | pull | Загрузка изменений | `Pulling updates`, `Found `+`new commit`, `Restoring local changes`, `stashing` | 15 |
| 4 | deps | Зависимости и бинарники | `Installing Node.js dependencies`, `Refreshing`, `Warming npx cache`, `Installing agent-browser`, `Installing cua-driver`, `install failed`, `download failed` | 15 |
| 5 | webui | Сборка веб-интерфейса | `Building web UI` | 10 |
| 6 | desktop | Пересборка приложения Hermes | `Checking if desktop app needs rebuilding`, `Installing desktop workspace dependencies`, `Building desktop packaged app`, `Packaging the desktop app`, `stage-native-deps`, `set-exe-identity`, `assert-dist-built` | 30 |
| 7 | config | Навыки и конфигурация | `Syncing bundled skills`, `Checking configuration for new options`, `config format updated` | 10 |
| 8 | done | Завершение | `Update complete`, `Gateway started` | 5 |

Правила классификации:
- Строка может относиться к этапу по первому совпадению в порядке таблицы; если совпадений нет —
  относится к текущему активному этапу (или к «общий лог», если этапа ещё нет).
- Строка с `✗` или `[ERROR]` или `failed`/`Error` (кроме строк, где `failed` часть нормального
  текста типа «never changes your conversations») увеличивает счётчик ошибок и подсвечивается в логе
  красным; при этом этап НЕ считается завершённым.
- Счётчик «соединений»: строки, содержащие `https://` и (`Fetching`, `download`, `Installing`,
  `Refreshing`, `Warming`, `Fetching updates`). Счётчик «загрузок»: строки с `download`,
  `Downloading`, `Installing`, `Warming`, `Found `+`commit`.
- Строка `Update complete` (или `✓ Code updated`) forcibly завершает этап done: прогресс = 100%.

## Прогресс

`progress = сумма весов завершённых этапов + 0.5*вес текущего` (когда текущий запущен),
`100` после `Update complete`. Полоса — ttk.Progressbar (determinate) плюс текстовый процент.
Переход прогресса только вперёд (никаких откатов назад).

## Тестовый режим (для самопроверки без реального апдейтера)

Флаг `--mock <path>`: вместо реального апдейтера запустить
`venv\Scripts\python.exe <path>` (тот же разбор строк/этапов). Флаг `--check`: реальный апдейтер
с аргументами `update --check --branch main` (тогда финальный баннер «Проверка завершена» /
«Обновление доступно: ...» — взять из строк `Update available` / `already up to date`).
Аргументы скрипта: `--check`, `--mock <path>`, `--repo <path>` (по умолчанию
`%LOCALAPPDATA%\hermes\hermes-agent`).

## Стиль

Тёмная тема: фон `#101418`, панели `#171c22`, текст `#e6e6e6`, акцент `#7aa2f7`, успех `#3fb950`,
ошибка `#f85149`, предупреждение `#d29922`, рамка `#30363d`. Шрифт лога Consolas 9.
Заголовок окна: «Hermes — обновление». В шапке окна: название текущего этапа крупно + таймер.
Слева колонка этапов (высота строки ~28, текущий подсвечен акцентом, завершённые ✓ зелёным),
справа лог. Полоса прогресса во всю ширину под шапкой. Счётчики (соединения/загрузки/ошибки)
мелким шрифтом в строке под полосой. Финальный баннер — плашка во всю ширину над кнопками.

## Ограничения

- Один файл, без классов-обёрток поверх tkinter (допустим один класс приложения).
- Никаких сетевых запросов из GUI напрямую — только дочерний процесс апдейтера.
- Не запускать сам апдейтер при старте без подтверждения: окно стартует с большой кнопки
  «Начать обновление» (и «Только проверка» рядом). После нажатия кнопки исчезают.
  Исключение: если скрипт вызван с `--check` или `--mock` — стартовать сразу.
- Все пути через os.path.expandvars/expanduser; лог-папку создать (os.makedirs exist_ok).
- Дочерний процесс запускать с env: `PYTHONIOENCODING=utf-8` (иначе кириллица/✓/✗ в pipe
  придут в cp1251 и лог сгниёт), чтение pipe в GUI — `encoding="utf-8", errors="replace"`,
  `text=True`, строки стрипать справа (`rstrip()`), `\r` игнорировать.
- Обработать отсутствие `hermes.exe`: красный баннер «hermes.exe не найден по пути ...» без запуска.
- Код должен выдержать: апдейтер уже запущен вторым экземпляром GUI (проверка: если в репо есть
  свежий lock-файл `%LOCALAPPDATA%\hermes\logs\update.lock`? — НЕ надо, вместо этого просто
  не делать этой проверки; но нельзя падать, если дочерний процесс умер сразу).

## Критерии приёмки (проверяются командой)

1. `pythonw -m py_compile hermes_update_gui.py` без ошибок (проверяет `python -m py_compile`).
2. `python hermes_update_gui.py --mock mock_ok.py` доходит до зелёного баннера «ОБНОВЛЕНИЕ ЗАВЕРШЕНО»,
   прогресс 100%, счётчики >0, лог-файл создан и содержит `[gui]` строки старта/финала.
3. `python hermes_update_gui.py --mock mock_fail.py` доходит до красного баннера с exit code и
   последними ошибочными строками.
4. Ни одного traceback в консоли/логе при обычном прогоне.
